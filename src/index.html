EvoMesh

A local-first environment where persistent agents live, communicate, acquire reusable skills, and evolve in isolated generations.

EvoMesh is not a cloud service and an agent is not merely a prompt. The environment owns lifecycle, messaging, state, permissions, model access, skills, health, and evolutionary history. The v0.1 foundation runs on a local machine with SQLite and local model endpoints.

Experimental software. EvoMesh application permissions are not an OS security sandbox. Review candidate mutations before promotion.

Core principles

  • Local first: startup requires no OpenAI, Anthropic, Gemini, or other cloud account.
  • The environment is the system: agents use environment messaging and services rather than private addresses.
  • Structured minds: beliefs, goals, intentions, skills, and permissions are persisted data.
  • Generational evolution: mutations happen in candidate workspaces, never in the active source tree.

Architecture

Human ──▶ Channel ──▶ EvoMesh Environment
                         ├─ Agent registry and lifecycle
                         ├─ Async message bus and mailboxes
                         ├─ SQLite persistence
                         ├─ Skill registry ──▶ filesystem policy
                         ├─ local model providers
                         └─ candidate workspace ──▶ validation

External supervisor metadata: ACTIVE ◀──▶ LAST-KNOWN-GOOD
                                      └──▶ CANDIDATE

Quick Start

Install Python 3.13+, Git, uv, and optionally Ollama.

git clone https://github.com/Dev-Art-Solutions/EvoMesh.git
cd EvoMesh
uv sync
cp evomesh.yaml.example evomesh.yaml
uv run evomesh

On PowerShell, replace cp with Copy-Item. The host still reaches READY when the model endpoint is unavailable and explains what must be fixed; inference waits for a healthy provider.

Environment

The explicit Environment service coordinates registry, lifecycle, bus, persistence, skills, grants, providers, and health. It boots the four system agents—Agent Architect, Guardian, Evaluator, and Environment Evolver—and restores user agents from SQLite.

Messaging and persistence

Every agent owns a mailbox. Direct and broadcast messages carry conversation and correlation IDs and are saved before delivery. SQLite migrations create durable records for agents, messages, skills, assignments, grants, environment state, and mutation history.

Agents

An agent definition contains stable identity, type, generation and parentage, purpose, provider/model, mind state, skills, permissions, memory behavior, lifecycle state, and timestamps. Runtime loops observe mailbox messages, call the configured local model, and return correlated responses through the bus.

BDI-inspired mind

Beliefs, goals, and intentions provide the initial cognitive shape. They are structured state, not a large hidden system prompt, and the architecture allows a later cognition strategy to replace BDI.

Agent Architect

Select Architect, describe the need, then answer its questions about name, purpose, constraints, filesystem access, and skills. It builds a candidate definition. /confirm activates and persists it; /cancel discards it.

evomesh> /chat architect
evomesh> Create a research agent
architect> What should the new agent be called?

Skills

The shared registry supports discovery, attachment, and invocation. Initial built-ins are Filesystem Read/Write, Markdown Read/Write, and Git Status/Diff. Missing capabilities return a structured missing-skill error. Automatic skill generation is planned.

Filesystem grants

Having a file skill does not grant path access. EvoMesh resolves paths before comparison, checks the requested operation, persists grants, and raises a structured denial when no matching ancestor grant exists.

/grant Researcher D:/Papers read
/grant Researcher D:/Research write
/revoke Researcher D:/Papers
These controls constrain EvoMesh skills. They do not claim to contain arbitrary native processes or hostile code at the operating-system level.

Local Models

Ollama

The default adapter checks /api/tags, reports whether the configured model is installed, and calls /api/generate.

InferHub

InferHub is an optional local/self-hosted provider through its OpenAI-compatible endpoint. EvoMesh does not require it.

OpenAI-compatible local endpoint

The generic adapter supports local servers exposing /models and /chat/completions. “OpenAI-compatible” describes the wire format, not a cloud dependency.

Evolution and generations

The Environment Evolver creates a numbered candidate copy that excludes active data, Git internals, virtual environments, and generations. The small external supervisor records active, last-known-good, and candidate metadata atomically.

Generation N (ACTIVE)
  └─ create isolated N+1 (CANDIDATE)
       ├─ uv sync
       ├─ ruff
       ├─ pyright
       └─ pytest
            PASS: eligible for human promotion
            FAIL: active N remains untouched

Validation results and mutation objectives are persisted. Human-confirmed promotion and rollback metadata exist; autonomous production promotion is deliberately out of scope for v0.1.

Configuration

Copy evomesh.yaml.example to evomesh.yaml. Configure the environment name, SQLite path, generations path, log level, default provider, endpoint, and model. Keep secrets out of Git.

models:
  default_provider: ollama
  providers:
    ollama:
      base_url: http://127.0.0.1:11434
      model: qwen3

CLI / Console

/help              /status             /agents
/skills            /chat <agent>       /confirm
/grant ...         /revoke ...         /evolution status
/exit

Plain text goes to the selected agent. The console implements a channel contract so future adapters can be added without changing agent logic.

Project Status

Implemented in v0.1 foundation: local boot, SQLite migrations, system-agent registry, async messaging, Architect interview and persistence, grants, shared built-in skills, model health, isolated candidate creation, validation commands, supervisor metadata, CI, and mock-backed tests.

Experimental: model reasoning behavior, mutation authoring, Git lineage, and promotion workflow. Not implemented: hardened OS sandbox, web UI, Telegram, PDF/OCR, distributed runtime, cloud providers, or automatic production promotion.

Roadmap

Next: controlled model-authored patches and structured Git commits; Skill Architect and skill generation; richer memory; web and Telegram channels; benchmarks; stronger process isolation; and policy-driven promotion.

Built with

Python 3.13, asyncio, Pydantic, SQLite/aiosqlite, HTTPX, uv, Ruff, Pyright, pytest, Git, and local models such as Ollama or InferHub.
